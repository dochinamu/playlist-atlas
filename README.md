# Playlist Atlas

플레이리스트를 오디오에서 직접 분석해 서로 비교하는 페이지. 브라우저에서만 돌아가고
서버도 API 키도 없다. `index.html` 하나가 전부다.

**데모: https://dochinamu.github.io/playlist-atlas/**

## 왜 직접 계산하나

[Statify](https://kyungyunlee.github.io/projects/statify/) 같은 프로젝트는 Spotify Web API가
미리 계산해 준 danceability·energy·valence를 받아서 그렸다. 그 길은 지금 막혀 있다.

- Spotify는 2024년 11월 27일 `audio-features`, `audio-analysis`, `recommendations`를
  그 날짜 이후 생성된 앱에 대해 폐기했고, 2026년 현재 대체 엔드포인트가 없다.
  새 앱으로 호출하면 토큰이 멀쩡해도 403이다.
- Extended Quota는 법인 등록과 월 활성 사용자 25만 명을 요구해 개인 프로젝트는 해당이 없다.
- Development Mode는 개발자가 Premium이어야 하고 허용 사용자가 25명으로 제한된다.
  즉 로그인을 붙여도 **링크를 받은 사람이 열 수 없다.**

그래서 같은 종류의 지표를 오디오에서 FFT로 직접 구했다. 결과적으로 이쪽이 할 말이 더 많다.

## 무엇을 재나

| 측정값 | 정의 | Spotify 대응 |
|---|---|---|
| RMS dBFS | 프레임 RMS 적분. LUFS 아님, 상대 비교용 | loudness |
| 크레스트 dB | `20·log10(peak/RMS)`. 작을수록 세게 압축 | — |
| 밝기 Hz | spectral centroid, 프레임 에너지 가중 | — |
| 롤오프 Hz | 스펙트럼 에너지 85% 지점 | — |
| 잡음성 | spectral flatness (기하평균/산술평균) | acousticness 대용 |
| 온셋/초 | 플럭스 곡선의 국소 최대 개수 | — |
| 박자 명료도 | `주기성 × min(1, 플럭스세기/0.25)` | **danceability 대용** |
| BPM | 온셋 자기상관 피크, 포물선 보간 | tempo |
| 조성 | 크로마 → Krumhansl–Schmuckler | **valence 대용 (장/단조)** |

`instrumentalness`(보컬 유무)와 `liveness`(라이브 여부)는 **넣지 않았다.** 학습 모델 없이는
신뢰할 만하게 추정되지 않는다. 추정치에 Spotify 라벨 이름을 붙이지 않은 것도 같은 이유다.

## 신호 처리

모노 합산 → 22.05 kHz 리샘플 → **곡 가운데 60초**만 분석(인트로·아웃트로 회피). Hann 창
1024, 홉 512(≈43 프레임/초). FFT는 radix-2 Cooley–Tukey를 직접 구현했고 Web Worker에서 돈다.
워커를 못 띄우는 환경(일부 브라우저의 `file://`)에서는 같은 코드가 메인 스레드로 떨어진다.

**크로마는 별도로 FFT 4096**(5.4 Hz)을 쓴다. 특징 추출용 1024(21.5 Hz)로는 가온다 근처
반음(15 Hz)을 가르지 못해 단3화음과 장3화음이 구분되지 않는다. 빈마다 반음 중심에서 얼마나
가까운지로 가중하고 130–2100 Hz만 쓴다.

**템포에는 관문이 둘이다.** 자기상관 피크를 곡선 에너지로 나눈 *주기성*과, 플럭스 합을
스펙트럼 크기 합으로 나눈 *플럭스 세기*. 주기성만 쓰면 척도에 무관한 값이라 거의 정지한
음에 남는 작은 주기적 잔물결도 1에 가깝게 나온다. 둘 다 넘을 때만 BPM을 보고한다.

**지도는 PCA.** 위 측정값들과 MFCC 12개를 합친 23차원을 z-표준화한 뒤 2축에 투영한다.
t-SNE가 아니라 PCA를 쓴 이유는 결정론적이고, 축이 무엇의 조합인지 말할 수 있고, 설명 분산을
숫자로 보고할 수 있기 때문이다.

## 검산

페이지를 열면 합성 기준 신호를 같은 분석기에 통과시켜 맨 아래 표에 보여준다. 알려진 입력에
대한 기대값과 실측:

| 입력 | 기대 | 실측 |
|---|---|---|
| 1 kHz 사인파 | centroid 1000 Hz, 크레스트 3.01 dB | 1000 Hz, 3.0 dB |
| 핑크 노이즈 | 잡음성 높음, 박자 없음 | 0.705, BPM `—` |
| 킥 루프 100 BPM | 100 BPM, 밝기 낮음 | 99.7 BPM, 597 Hz |
| C 장3화음 | C major | **C major** (r=0.88) |
| C 단3화음 | C minor | **C minor** (r=0.90) |
| A 장3화음 | A major | **A major** (r=0.88) |
| F# 단3화음 | F# minor | **F# minor** (r=0.92) |
| 합성 클럽 비트 122 / 104 | 122 / 104 BPM | 122.8 / 103.6 BPM |
| 지속 패드 | 박자 없음 | BPM `—` |

## 띄우기

```bash
python3 -m http.server 8000
# http://localhost:8000
```

`?nw=1`을 붙이면 Web Worker 대신 메인 스레드에서 분석한다(디버깅·헤드리스 렌더링용).

## 한계

- RMS는 물리량이다. 지각 라우드니스는 K-weighting(ITU-R BS.1770)으로 바꿔야 한다.
- BPM은 4/4 균일 박자를 가정한다. 하프타임·루바토·변박에서 틀린다.
- 조성은 곡 전체를 한 값으로 요약한다. 조바꿈이 잦은 곡에는 맞지 않는다.
- 박자 명료도의 두 문턱값(0.22 / 0.25)은 합성 신호로 정했다. 실제 음원 데이터셋으로
  다시 적합해야 한다.
- 디코딩은 곡 전체를 해야 하므로 긴 플레이리스트는 디코딩이 전체 시간을 지배한다.
- 플레이리스트는 4개까지 비교한다. 색각 분리를 지키며 쓸 수 있는 범주형 색 수의 한계다.
